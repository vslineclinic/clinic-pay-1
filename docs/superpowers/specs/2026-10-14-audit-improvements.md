# clinic-pay 감사 개선 개발 범위

사용자는 2026-10-14 감사 항목 12(서버 API 키 입력칸 기본값)를 제외한 나머지 개선 개발을 승인했다. 새 정산 시스템으로 재작성하지 않고 현재 Streamlit 앱의 정산 정확성·입력·출력·데이터 보호·성능을 고친다. 디자인은 최신 VS Line 지출관리앱 clinic-expense-ledger의 실제 색상·폰트·로고 큰틀을 참조한다.

## 제약
- 감사 12의 GOOGLE_API_KEY → 비밀번호 입력칸 기본값 전달 동작은 유지한다.
- 결정론적 계산, 베가스 마감 기준 부호, import-safe, 정식 사용자 용어를 유지한다.
- 환자 실데이터·자격증명을 테스트/커밋/외부 AI에 보내지 않는다. 합성 데이터만 사용한다.
- 모호한 승인번호·동명이인·부분 연결로 원장 수정 방향을 확정하지 않는다.
- 원본 외부 시트 ACL과 배포 비밀값은 임의 변경하지 않는다. 필요한 운영 설정은 문서화한다.
- 소스는 분리 브랜치에서 개발하고 GitHub PR로 전달한다. main 병합·운영 배포는 하지 않는다.
- 새 월간 DB·검토 업무 저장 시스템 등 별도 대형 기능은 이번 19개 감사 개선 범위에 포함하지 않는다.

## 승인된 감사 개선 항목

### 1. 단일 날짜 파일은 선택 날짜와 달라도 통과합니다
문제: 날짜가 여러 개일 때만 일치 여부를 확인합니다. 선택일이 5월 12일이어도 5월 11일만 들어 있는 파일은 그대로 반환됩니다. 재방문 환자 번호가 겹치면 뒤의 교차검증도 통과합니다.
수정 방향: 하루짜리 파일에도 선택일과 원본끼리의 날짜 일치를 확인합니다. 날짜를 확인할 수 없는 자료는 불일치와 구별해 검증 불가로 표시합니다.
재현 근거: 합성 입력 실행: 선택 2026-05-12 / 원본 2026-05-11 → error가 빈 문자열. 실제 운영 파일은 사용하지 않았습니다.
기존 위치: app.py:4606-4666

### 2. 기간 분석이 금액이 다른 거래를 원인 목록에서 지웁니다
문제: 승인번호만 같으면 금액·채널·취소 방향 확인 없이 연결 완료로 처리합니다. 정상과 취소가 함께 있다는 이유만으로 잔액이 0인지 확인하지 않고 상쇄하기도 합니다.
수정 방향: 동일 승인번호 그룹의 채널·방향·순금액까지 확인합니다. 거래 연결과 금액 대사 완료를 구분하고, 연결된 거래라도 차이가 있으면 목록에 남깁니다.
재현 근거: 합성 입력 실행: 같은 승인번호의 단말기 50,000원 / 베가스 60,000원 → 차이 -10,000원, 양쪽 잔여 거래는 0건.
기존 위치: app.py:2264-2323

### 3. 정상 취소 거래를 확정 오류 후보로 표시합니다
문제: 단말기 쪽은 정상 승인만 합산하지만 베가스 쪽은 취소를 포함한 순금액을 씁니다. 동일한 정상·취소 거래라도 비교 기준이 달라집니다.
수정 방향: 두 원본 모두 승인에서 취소를 뺀 순금액으로 통일합니다. 공통 계산을 재사용하고, 원인 추정은 수정 명령으로 표시하지 않습니다.
재현 근거: 합성 입력 실행: A의 승인 50,000원 + 취소 50,000원은 세 원본에서 모두 순금액 0원. B의 실제 1,000원 차이를 함께 넣으면 정상인 A도 50,000원 차이의 ★★ 최우선 후보로 표시됩니다.
기존 위치: app.py:2735-2739,2804-2869

### 4. 일부 승인내역을 전체 금액으로 보고 오류 원장을 단정합니다
문제: 환자에게 결제가 여러 건 있어도 승인번호로 연결된 일부 금액을 전체 단말기 금액처럼 사용합니다. 연결되지 않은 나머지 거래가 있는지 확인하지 않습니다.
수정 방향: 연결 범위와 미연결 건수를 함께 계산합니다. 전체 거래가 확인된 경우에만 원장 위치를 강하게 판단하고, 부분 연결이면 근거 부족으로 표시합니다.
재현 근거: 합성 입력 실행: 실제 30,000+20,000원, 베가스 50,000원, 일일마감 30,000원, 승인 연결은 30,000원만 → 베가스 쪽 오류 확정적이라는 잘못된 판정.
기존 위치: app.py:2642-2687,4207-4235,4360-4376

### 5. 동명이인·동일 금액에서 차트번호 오타를 임의 확정합니다
문제: 같은 이름·같은 금액의 후보가 여럿이어도 첫 번째 최고 점수 후보를 선택합니다. 동률의 모호함을 남기지 않고 유형B로 확정해 후속 집계에 병합합니다.
수정 방향: 양방향으로 후보가 하나뿐일 때만 자동 연결합니다. 동률과 다대일은 별도의 미확정 후보로 남기고 금액을 병합하지 않습니다.
재현 근거: 합성 입력 실행: 베가스 100·900번에 동일 이름/50,000원, 일일마감 555번에 같은 이름/50,000원 → 555→100으로 선택되어 900만 누락으로 표시.
기존 위치: app.py:2572-2616,4256-4320

### 6. 긴 승인번호의 앞자리를 버려 다른 거래를 합칩니다
문제: 파서는 5~10자리 승인번호를 지원하지만 두 귀속 경로는 끝 8자리만 사용합니다. 앞자리만 다른 긴 승인번호가 같은 거래로 합쳐집니다. 전체 번호를 보존하는 공통 _appr_key가 이미 있어 중복 규칙을 제거할 수 있습니다.
수정 방향: 전체 승인번호를 보존하는 검증된 공통 정규화 함수를 모든 경로에 적용합니다. 날짜·채널 등 보조 조건을 확인하고 충돌은 미확정으로 처리합니다.
재현 근거: 합성 입력 실행: 112345678과 212345678이 끝 8자리 규칙으로 충돌해 잘못된 환자 금액으로 합산됩니다.
기존 위치: app.py:143-159,2656-2679,2810-2812

### 7. 기간 분석에서 플랫폼만 다른 날짜는 상세 확인에서 빠집니다
문제: 플랫폼 합계는 읽지만 플랫폼 차이 열을 만들지 않고, 상세 확인할 날짜도 카드·현금 차이로만 선정합니다.
수정 방향: 일일마감-베가스 플랫폼 차이를 계산하고 차이 날짜·요약·상세·내보내기에 같은 기준으로 포함합니다.
재현 근거: 합성 입력 실행: 카드·현금 일치 / 일일마감 플랫폼 30,000원 / 베가스 플랫폼 50,000원 → -20,000원인데 차이 날짜가 비어 있음.
기존 위치: app.py:2416-2494,4694-4700,4761-4763

### 8. 2파일 보조 화면은 환불을 차감하지 않습니다
문제: 메인 집계는 환불을 차감하지만 이 화면은 일일마감 본행의 양수 카드 금액만 더합니다. 같은 분석 안에서 결과가 서로 다릅니다.
수정 방향: 이 화면의 별도 합산을 없애고 환불을 반영하는 공통 환자별 집계를 사용합니다.
재현 근거: 화면 집계 블록 그대로 실행: 본행 100,000원 - 환불 20,000원 / 베가스 80,000원 → 메인 0원, 상세 +20,000원.
기존 위치: app.py:5399-5429

### 9. 엑셀 요약의 플랫폼 차이 열 제목이 계산과 다릅니다
문제: 플랫폼 행에 베가스-일일마감 값을 계산해 넣으면서 열 제목은 차트-한솔(P1)로 표시합니다. 단말기가 비교 대상이 아닌 플랫폼 칸도 0으로 채웁니다.
수정 방향: 별도 요약 계산을 삭제하고 검증된 채널 대사표를 재사용합니다. 비교 대상이 아닌 값은 빈칸 또는 대상 아님으로 남기고 차이 부호를 통일합니다.
재현 근거: 합성 내보내기 확인: 플랫폼 베가스 120,000원 / 일일마감 100,000원 차이 20,000원이 차트-한솔 열에 기록됩니다.
기존 위치: app.py:3932-3956

### 10. 제공하는 표준 CSV 양식을 업로드하면 파싱이 실패합니다
문제: load_file이 첫 행을 열 이름으로 소비하지만 parse_daily는 데이터 행 안에서만 머리글을 찾습니다. 정상 템플릿을 넣어도 데이터가 없는 것으로 반환합니다.
수정 방향: 파일 로더와 파서의 머리글 규칙을 통일합니다. 기존 단말기 CSV 파서에 미칠 영향을 확인하면서 제공 템플릿을 실제 업로드 경로로 통과시키는 회귀 검증을 추가합니다.
재현 근거: 저장소 표준 CSV를 load_file→parse_daily로 실행: 본행 0 / 환불 0. 같은 바이트의 머리글을 보존하면 본행 4 / 환불 1. 기존 테스트는 load_file을 건너뛰어 이 문제를 놓칩니다.
기존 위치: app.py:328-333,966-974; tests/test_parsers.py

### 11. 구글시트 대체 읽기의 오래된 캐시가 다른 날짜를 받아들입니다
문제: 첫 시트 내용의 지문을 세션에 한 번만 저장합니다. 첫 시트가 수정된 뒤 존재하지 않는 날짜를 요청하면 새 내용이 옛 지문과 다르다는 이유로 요청한 날짜의 자료로 받아들입니다.
수정 방향: 탭 존재 여부를 독립적으로 확인하거나 대체 응답 검증 근거를 매 조회 시 갱신합니다. 검증에 실패하면 확인 불가로 멈추고, 오래된 내용 지문의 차이를 날짜 증명으로 사용하지 않습니다.
재현 근거: 모든 네트워크를 합성 응답으로 대체: 정상 6/2 조회 후 첫 시트 수정 → 없는 6/3 요청이 첫 시트 내용으로 성공. 같은 요청을 새 캐시로 하면 정상적으로 LookupError. export/gid 경로가 불가해 gviz 대체 경로를 쓰는 조건에서 재현했습니다.
기존 위치: app.py:677-709,4924,5049

### 13. 입력 문자열이 엑셀 수식으로 저장됩니다
문제: 문자열을 그대로 openpyxl에 전달하므로 =로 시작하는 값이 수식 셀로 저장됩니다. 검증 자료에 입력된 문자열이 실행 가능한 수식이 됩니다.
수정 방향: 외부에서 온 텍스트 열은 수식으로 해석되지 않게 문자 셀로 기록합니다. 숫자 금액 열은 숫자로 유지하고, 모든 엑셀 내보내기에 같은 규칙을 적용합니다.
재현 근거: 무해한 합성 이름 =1+1로 재현: 검증 엑셀 D2의 data_type이 f. 통합 엑셀의 여러 시트에서도 수식 셀 확인. 실제 공격 수식은 사용하지 않았습니다.
기존 위치: app.py:3867-3960,4417-4426

### 14. 공개 소스·인증 없는 시트 읽기 설계를 운영 권한과 함께 점검해야 합니다
문제: GitHub 저장소는 공개이며 코드에 시트 식별 주소가 있습니다. README는 링크 공개 공유를 요구하고 앱 내부에는 로그인·지점별 권한 검사가 없습니다. 문서·주석에는 실사례로 서술한 식별정보와 금액도 있어 가명화 점검이 필요합니다.
수정 방향: 원본 시트는 비공개 인증 방식으로 바꾸고 사용자 지점 권한을 검사합니다. 주소·비밀번호는 안전한 설정으로 옮기고, 실제 값 여부를 확인해 문서와 필요한 과거 이력의 식별정보를 정리합니다.
재현 근거: 공개 저장소와 인증 없는 요청 코드는 확인했습니다. 실제 시트 공유 상태, 실사례 이름의 진위, 배포 앞단 인증·접근 로그는 확인하지 않았으므로 현재 유출됐다고 단정하지 않습니다.
기존 위치: app.py:65-76,326,447-463,4944-5054; README.md:37-55

### 15. AI 전송 전 환자 식별자를 줄이는 단계가 없습니다
문제: 이름·차트번호·승인번호와 수납 내역이 분석 텍스트에 포함됩니다. 사전 미리보기와 실행 버튼은 있으나, 이름/내부번호를 임시 토큰으로 바꾸는 가명처리 단계는 없습니다.
수정 방향: 서버에서 예시 P001/A001 같은 분석용 토큰을 만들고 응답 후 내부에서만 원래 기록으로 연결합니다. 외부 전송에 필요한 최소 필드만 허용하며 공급자·보존·계약 설정을 운영 담당자가 확인합니다.
재현 근거: 전송 문자열 조립과 API 호출 경로 확인. 운영 환자 정보를 외부로 보내거나 현 계약 조건을 조사하지 않았으며, 법률 위반 판단은 이 감사 범위가 아닙니다.
기존 위치: app.py:3120-3578,4554-4577,5481-5493

### 16. AI 캐시가 만료 없이 평문으로 남고 결과 출처도 혼동됩니다
문제: 결과를 평문 JSON으로 저장하고 ts는 기록만 하며 만료에 쓰지 않습니다. 키는 데이터+질문만 포함하므로 모델·프롬프트가 바뀌어도 예전 답을 재사용하고, 파일 캐시 응답에 현재 선택 모델명을 붙입니다.
수정 방향: 필요 없다면 세션 범위 캐시만 남깁니다. 보존이 필요하면 가명화, 접근 범위, TTL, 정리 정책과 데이터·프롬프트 버전·실제 모델 메타데이터를 적용합니다.
